# 实现文档

## 交付目标

说明系统如何实现需求：不懂代码的人能理解运转过程，开发者能定位改动并据此实施。

- 需求背景点到为止，主体是实现逻辑，不重复堆列需求。
- 保留理解实现所必需的设计取舍及其原因，不展开无关的选型报告。
- 用自然语言讲清逻辑；代码、配置和接口示例仅作必要补充，不以调用链代替解释。
- 篇幅与复杂度相称，不凑章节、不重复同一信息。

## 事实与边界

- 说明既有系统时，以实际代码、配置和接口为依据，名称必须可定位。
- 描述开发方案时，区分现有机制、拟新增内容和待确认事项；拟新增名称明确标注。
- 数字、限制和时序来自已确认需求或实现；未确定时标注待定，并给出建议及影响。
- 评审文档时，先说明问题、依据与修改建议，不擅自将评审扩展为代码实现。

## 内容

默认包括“整体思路”和“实现逻辑”；小改动可只写实现逻辑。

每块实现交代相关的内容，不强行套表：

- **入口**：谁在什么动作或事件下触发，如何定位入口。
- **数据**：读取或修改什么，关键字段和状态的业务含义。
- **流程**：判断条件、处理步骤、状态变化，以及与此流程有关的失败和并发行为。
- **结果**：用户和系统可观察到的结果。
- **落点**：涉及的模块或文件，各自承担什么职责。

需求较多时补充“需求 → 实现位置 → 验证标准”的对应关系；按需交代兼容、迁移和影响范围。

例如：

> 用户提交订单后，系统在 `OrderService.create` 校验库存。不足时终止并提示；充足时，在同一事务中创建待支付订单并扣减库存，任一步失败则回滚。支付成功后订单进入已支付状态，再通知仓储备货。通知失败进入已有重试流程。

这个例子仅说明表达方式，不代表目标项目具有相同的类名、事务或重试机制。

## 表达与验收

- 名称嵌入解释，避免只有“调用 A → 调用 B”的流水账。
- 简单流程用行文，复杂分支或状态关系用表格或图，不强制所有分支都画图。
- 验证标准描述可观察的行为和结果，不能只写“功能正常”。
- 交付前核对需求覆盖、名称与依据、失败行为和待确认事项；建议验证的方法不等于已经执行的验证。

## 输出

默认 Markdown，用户指定格式时按其要求。
明确要求 HTML 或网页视觉排版时使用 `tmjwx-give-me-html`；仅“发给别人看”不改变格式。该技能不可用时说明情况，并按用户要求直接制作，不因可选技能缺失中断内容交付。
